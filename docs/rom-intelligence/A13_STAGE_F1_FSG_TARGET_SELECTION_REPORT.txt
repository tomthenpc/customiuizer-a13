3. REAL_FORCE_FSG_NAV_BAR polarity (F1-R1 correction)
-----------------------------------------------------
The getGlobalBoolean("force_fsg_nav_bar") hook captures the real ROM value
into REAL_FORCE_FSG_NAV_BAR and then returns true to BaseRecentsImpl.

- REAL_FORCE_FSG_NAV_BAR == false
  means the real Settings.Global "force_fsg_nav_bar" is false:
  the device is in 3-button/navigation-bar mode.
  This is the target hybrid state for controls_fsg_horiz:
  navigation bar present + horizontal/side back gestures enabled.

- REAL_FORCE_FSG_NAV_BAR == true
  means the real "force_fsg_nav_bar" is true:
  the device is already in native full FSG mode.
  The module must not introduce any third-party-home corrective.

The previous F1 report incorrectly assumed the corrective override should
happen when REAL_FORCE_FSG_NAV_BAR was true. The hybrid target is
REAL_FORCE_FSG_NAV_BAR == false.

8. Back-stub method audit
-------------------------
The stub add/remove methods do not themselves check mIsUseMiuiHomeAsDefaultHome.
They are controlled by updateFsgWindowState() and the addFsgGestureWindow()
condition block.

  - addBackStubWindow()V
      guards: !SpecialFDeviceGestureHelper.isInSFDeviceFoldedMode()
      executor: TouchInteractionService.BACKGROUND_EXECUTOR

  - showBackStubWindow()V
      guards: !SpecialFDeviceGestureHelper.isInSFDeviceFoldedMode()
      executor: TouchInteractionService.BACKGROUND_EXECUTOR

  - clearBackStubWindow()V
      guards: none
      executor: TouchInteractionService.BACKGROUND_EXECUTOR

  - removeNavStubView()V
      guards: none
      executor: TouchInteractionService.GESTURE_EXECUTOR.getHandler()

  - createAndAddNavStubView()V
      guards: !SpecialFDeviceGestureHelper.isInSFDeviceFoldedMode()
      executor: TouchInteractionService.GESTURE_EXECUTOR.getHandler()

Back-stub idempotence:
  - addBackStubWindow() lambda checks mGestureStubLeft == null before
    initGestureStub() and then calls showGestureStub() on left and right.
    Repeated calls are safe: no duplicate WindowManager addView if the
    fields are non-null.
  - showBackStubWindow() lambda reads force_fsg_nav_bar again, then
    initializes only if mGestureStubLeft == null. It is less direct for
    recovery because it re-reads the global.
  - clearBackStubWindow() lambda clears one side per run and nulls only
    the cleared pointer; the next addBackStubWindow() re-initializes both.
  - All back-stub operations run on the same BACKGROUND_EXECUTOR, so
    queued add/clear pairs are ordered.

9. Default-home switching lifecycle
-----------------------------------
Static lifecycle (exact APK):

  BaseRecentsImpl.<init>
      -> addFsgGestureWindow()
          -> mHasNavigationBar = DeviceConfig.isHasNavigationBar()
          -> mIsFsgNavBar = MiuiSettingsUtils.getGlobalBoolean("force_fsg_nav_bar")
                              [module publishes REAL_FORCE_FSG_NAV_BAR, returns true]
          -> mIsUseMiuiHomeAsDefaultHome =
                 Utilities.getDefaultHomePackageName(context).equals(packageName)
          -> updateUseLauncherRecentsAndFsGesture()
          -> if (mIsFsgNavBar && !mIsInAnotherPro && mIsUseMiuiHomeAsDefaultHome)
                 createAndAddNavStubView(); showBackStubWindow();

  TouchInteractionService.initWhenUserUnlocked()
      -> OverviewComponentObserver.getInstance()
      -> OverviewComponentObserver.updateOverviewTargets()
          -> resolve default home via PackageManager
          -> setIsUseMiuiHomeAsDefaultHome(mIsHomeAndOverviewSame)

  OverviewComponentObserver receives ACTION_PREFERRED_ACTIVITY_CHANGED
      -> updateOverviewTargets()

  BaseRecentsImpl$7 (power_supersave_mode_open observer) onChange
      -> setIsUseMiuiHomeAsDefaultHome(
             Utilities.getDefaultHomePackageName(context).equals(packageName))
      -> OverviewComponentObserver.getInstance().updateOverviewTargetsPost()

addFsgGestureWindow() does NOT call updateFsgWindowState(). Therefore an
updateFsgWindowState() after-hook alone cannot recover the back stub at boot;
an addFsgGestureWindow() after-hook is also needed.

10. Candidate corrective designs
--------------------------------
Design A: Hook Utilities.getDefaultHomePackageName to return "com.miui.home"
  - Risk: HIGH. Rejected. Affects FallbackHomeCompat, Poco, settings UI,
    elderly-mode receiver, nav-bar dialog, etc.
  - Rank: REJECTED

Design B: Hook BaseRecentsImpl.addFsgGestureWindow + setIsUseMiuiHomeAsDefaultHome
  Previous F1 report incorrectly recommended this design.
  - It forces mIsUseMiuiHomeAsDefaultHome = true.
  - It calls updateUseLauncherRecentsAndFsGesture(), which writes
    use_gesture_version_three = true.
  - It may decouple mIsUseMiuiHomeAsDefaultHome from
    OverviewComponentObserver.mIsHomeAndOverviewSame.
  - Risk: HIGH.
  - Rank: REJECTED_UNSAFE_UNLESS_PROVEN

Design C: Hook only addFsgGestureWindow / updateFsgWindowState branch logic
  - Force stub-creation branch regardless of mIsUseMiuiHomeAsDefaultHome.
  - Risk: MEDIUM-HIGH. Still has to avoid nav stub and may leave
    use_gesture_version_three false.
  - Rank: 3

Design E: Back-stub-only recovery (selected)
  - Add addFsgGestureWindow() after-hook and extend updateFsgWindowState()
    after-hook.
  - In hybrid conditions (REAL=false, mHasNavigationBar, !mIsInAnotherPro,
    !isFolded, mIsUseMiuiHomeAsDefaultHome=false), call addBackStubWindow().
  - Leaves mIsUseMiuiHomeAsDefaultHome, getDefaultHomePackageName,
    OverviewComponentObserver, and use_gesture_version_three untouched.
  - Reuses native addBackStubWindow() and GestureStubView.showGestureStub().
  - Does not create nav stub; existing createAndAddNavStubView before-hook
    already skips nav stub when REAL=false.
  - Rank: 1 (SELECTED)

12. Minimum future behavior tests
---------------------------------
F1-T1: MiuiHome default + REAL=true + feature=true
  mIsUseMiuiHomeAsDefaultHome true; nav stub and back stub created.

F1-T2: MiuiHome default + REAL=false + feature=true
  mIsUseMiuiHomeAsDefaultHome true; nav stub suppressed by existing hook;
  back stub created.

F1-T3: Third-party default + REAL=false + feature=true
  addFsgGestureWindow() after-hook and updateFsgWindowState() after-hook
  recover back stub; nav stub absent.

F1-T4: Third-party default + REAL=true + feature=true
  No recovery; native full FSG behavior.

F1-T5: Default home Xiaomi <-> third-party switching
  setIsUseMiuiHomeAsDefaultHome(false) triggers updateFsgWindowState(),
  which clears then recovers back stub. Switching to MiuiHome should not
  duplicate.

F1-T6: 3-button navigation fail-closed
  REAL=false but feature disabled -> no FSGesturesHook; no stub.

F1-T7: controls_fsg_horiz_apps package filter
  GestureStubView.onTouchEvent returns false for packages in set.

F1-T8: repeated updateFsgWindowState events
  No duplicate add and no race because all back-stub work uses the same
  BACKGROUND_EXECUTOR.

F1-T9: missing/unsupported target
  Hook silently skipped (fail-open).

13. Conclusion
--------------
Stage F1 static analysis is complete and corrected in F1-R1.
The default-home gate is the only statically demonstrated blocker for
horizontal FSG when a third-party launcher is the default.

The recommended F1 design (B) is REJECTED because it is unsafe and broader
than the stated requirement. The selected target is Design E: a back-stub-only
recovery that leaves default-home state, recents ownership, and the
use_gesture_version_three setting untouched.

No production change has been made in this batch.
Issue #2 remains UNVERIFIED at device level.
Production change requires an explicit corrective gate and real-device validation.
