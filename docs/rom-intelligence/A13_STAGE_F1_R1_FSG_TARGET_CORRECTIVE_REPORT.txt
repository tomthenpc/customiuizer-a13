================================
BACK STUB SAFETY
================================

SHOW_BACK_STUB_WINDOW_IDEMPOTENT:
  YES, with module caveat.
  - Wrapper checks !isInSFDeviceFoldedMode() and posts to BACKGROUND_EXECUTOR.
  - Lambda checks mHasNavigationBar argument; if false, does nothing.
  - If true, it reads force_fsg_nav_bar again. Module returns true for
    BaseRecentsImpl stack, so it continues.
  - If mGestureStubLeft == null, it calls initGestureStub(), which creates
    and adds two GestureStubView instances to WindowManager in the constructor.
  - Then it calls showGestureStub() on both.
  - On repeated calls, mGestureStubLeft is non-null, so it skips
    initGestureStub() and only calls showGestureStub() again.
  - GestureStubView.showGestureStub() removes delayed hide messages and
    sets keepHidden=0. Repeated calls are safe and do not duplicate
    WindowManager views.

ADD_BACK_STUB_WINDOW_IDEMPOTENT:
  YES.
  - Wrapper checks !isInSFDeviceFoldedMode() and posts to BACKGROUND_EXECUTOR.
  - Lambda: if mGestureStubLeft == null, calls initGestureStub() (creates
    and adds both GestureStubView to WindowManager), then
    mGestureStubLeft.showGestureStub() / mGestureStubRight.showGestureStub().
  - On repeated calls mGestureStubLeft is non-null, so it only re-shows.
  - It does NOT re-read force_fsg_nav_bar, making it more deterministic
    than showBackStubWindow() for recovery.

BACK_STUB_EXECUTOR_ORDERING:
  SAFE for add/clear pairing.
  - addBackStubWindow() and clearBackStubWindow() both run on
    TouchInteractionService.BACKGROUND_EXECUTOR, so calls from the same
    thread are queued and executed in order.
  - createAndAddNavStubView() and removeNavStubView() run on
    TouchInteractionService.GESTURE_EXECUTOR, independent of back stub work.
  - A native updateFsgWindowState() that clears back stub then a module
    after-hook that calls addBackStubWindow() will produce the sequence
    clear -> add on the same executor, which is safe.

CLEAR_BACK_STUB_WINDOW_BEHAVIOR:
  - Lambda: if mGestureStubLeft == null, only mGestureStubRight is cleared
    if present; otherwise mGestureStubLeft is cleared and set to null.
  - In normal ROM flow, both left and right are created together by
    initGestureStub(). The clear path only nulls one pointer, which is an
    existing ROM quirk, but the next addBackStubWindow() will re-run
    initGestureStub() and replace the still-referenced right pointer.

EXISTING_UPDATE_CALLBACK_SUFFICIENT:
  NO for initial boot; YES for runtime lifecycle.
  - updateFsgWindowState() is called by setIsUseMiuiHomeAsDefaultHome()
    on default-home changes and by observers when force_fsg_nav_bar changes.
  - However addFsgGestureWindow() (constructor) does NOT call
    updateFsgWindowState(). With third-party default at boot, the native
    if-block in addFsgGestureWindow() is skipped, so the stub is never
    created. The first setIsUseMiuiHomeAsDefaultHome(false) from
    OverviewComponentObserver sees no change and also does not call
    updateFsgWindowState().
  - Therefore a single updateFsgWindowState() after-hook alone does not
    recover the back stub at boot. An addFsgGestureWindow() after-hook is
    also required to cover the constructor path.
  - Once the system is running, updateFsgWindowState() after-hook is
    sufficient to recover when the user switches from MiuiHome to
    third-party default, because the setter will call updateFsgWindowState().

NATIVE_ELIGIBILITY_CONDITIONS (shouldRecoverBackStub):
  - mHasNavigationBar == true
  - !mIsInAnotherPro
  - !SpecialFDeviceGestureHelper.isInSFDeviceFoldedMode()
  - REAL_FORCE_FSG_NAV_BAR == false
  - controls_fsg_horiz == true (implicit: FSGesturesHook is installed)
  - mIsUseMiuiHomeAsDefaultHome == false (the third-party default condition)

Policy:

  shouldRecoverBackStub(
      featureEnabled,
      realForceFsgNavBar,
      hasNavigationBar,
      isInAnotherProfile,
      isFoldedMode,
      isMiuiHomeDefault):

      if !featureEnabled -> false
      if realForceFsgNavBar -> false
      if !hasNavigationBar -> false
      if isInAnotherProfile -> false
      if isFoldedMode -> false
      if isMiuiHomeDefault -> false
      return true

This matches the hybrid target: navigation bar present, real FSG off,
MiuiHome is NOT the default, and the feature is enabled.

  REJECTED.

DESIGN_B (mIsUseMiuiHomeAsDefaultHome field override):
  REJECTED_UNSAFE_UNLESS_PROVEN.
  - Changes use_gesture_version_three and default-home state;
  - risks affecting overview/recents ownership and foldable behavior.

DESIGN_C (branch override in addFsgGestureWindow / updateFsgWindowState):
  REQUIRES_PROOF.
  - Could force the stub-creation branch regardless of mIsUseMiuiHomeAsDefaultHome.
  - Still has to avoid creating the nav stub and avoid calling
    updateUseLauncherRecentsAndFsGesture with true.
  - More intrusive than Design E and re-implements native branch logic.

DESIGN_E (back-stub-only recovery):
  PREFERRED CANDIDATE.
  - Leaves mIsUseMiuiHomeAsDefaultHome untouched.
  - Leaves Utilities.getDefaultHomePackageName untouched.
  - Leaves OverviewComponentObserver and use_gesture_version_three untouched.
  - Preserves the existing REAL_FORCE_FSG_NAV_BAR fail-closed channel.
  - Extends the existing updateFsgWindowState after-hook with a
    guarded addBackStubWindow() call when hybrid conditions hold.
  - Adds an addFsgGestureWindow() after-hook to cover the boot-time path.
  - Reuses native BaseRecentsImpl.addBackStubWindow() and
    GestureStubView.showGestureStub(), which are idempotent on repeated calls.
  - Does not create nav stub; existing createAndAddNavStubView before-hook
    already skips nav stub when REAL=false.

SELECTED_TARGET: E (conditionally)
SELECTION_REASON:
  Design E is the narrowest change that satisfies the stated hybrid goal
  (navigation bar + horizontal/side back gestures) without mutating
  default-home identity, recents ownership, or the global
  use_gesture_version_three setting. Static evidence shows the back stub
  path can operate independently of that setting and is idempotent.
