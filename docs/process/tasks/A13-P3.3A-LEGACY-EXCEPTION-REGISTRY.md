## Ownership inventory generation logic

Current source of truth:
- `docs/audit/A13_HOOK_OWNERSHIP_INVENTORY.md` (committed, 676 total direct hook calls, 595 LEGACY_EXCEPTION).
- `tools/audit_hook_ownership.py` regenerates it by scanning production `*.kt`/`*.java` for `ModuleHelper|XposedHelpers|XposedBridge|HookerClassHelper` hook calls and classifying each per-file into:
  - `REGISTRY_FEATURE` if the file contains only hook calls inside functions referenced from `FeatureCatalog.kt` installer lambdas.
  - `INSTALLER_INFRASTRUCTURE` for explicit installer/bootstrap files and utility classes.
  - `API_BRIDGE` for `ModuleHelper.java` and `org/apache/commons/lang3/reflect`.
  - `LEGACY_EXCEPTION` for business hook files with at least one call not owned by the typed catalog.
  - `UNKNOWN` when no owner can be determined (target: 0).

Limitations to address in P3.3A:
- `tools/audit_hook_ownership.py` currently over-counts typed installer functions because it extracts the `installer = { ... }` body greedily across multiple `FeatureSpec` blocks.
- The markdown inventory only provides per-file totals; it does not expose stable call-site identity (file:line:enclosingFunction).
- Per-call classification is required before LEGACY_EXCEPTION records can reference specific call sites.

## Current category definitions

| Category | Meaning |
|---|---|
| `REGISTRY_FEATURE` | Hook implementation owned by a typed `FeatureId` and installed through `FeatureInstallRegistry`. |
| `INSTALLER_INFRASTRUCTURE` | Bootstrap / utility hook used by an `Installer` or shared runtime helper, not a business Feature. |
| `API_BRIDGE` | Framework bridge for hook reflection (e.g., `ModuleHelper`, `XposedHelpers`). |
| `LEGACY_EXCEPTION` | Business hook with at least one call site not yet owned by a typed catalog Feature, registered with owner/reason/exit condition. |
| `UNKNOWN` | Hook with no reachable owner (target: 0). |

## Exception ownership granularity

Each LEGACY_EXCEPTION record must correspond to one logical install owner, such as:
- a single installer route (e.g., `MainModule → Controls.PowerMenuHook`);
- a single preference activation entry (e.g., `system_separatevolume` cross-process volume step hook);
- an indivisible lifecycle/bootstrap owner (e.g., `HookInstaller` session helper);
- a cross-process owner (e.g., `VolumeSteps` routed to both `system_server` and `SystemUI`);
- a resource hook owner (e.g., `ResourceHooks.setResReplacement` family).

Prohibited:
- one record per hook call;
- one record per source file;
- one record for all 595 legacy calls;
- whole-file registration for mixed files;
- reason text that is only "legacy code".

A single exception can cover multiple hook targets if they share:
- the same entrypoint;
- the same logical owner;
- compatible process/phase;
- the same specific technical reason;
- the same test evidence;
- the same exit condition.

## Registry schema

Each record must contain at least the following fields:

```json
{
  "id": "stableUniqueId",
  "status": "ACTIVE",
  "owner": "logical owner",
  "sourceFile": "repository-relative path",
  "entrypoint": "installer or hook entrypoint",
  "process": "system_server|system_ui|launcher|android|per_app|resource|other",
  "phase": "SYSTEM_SERVER_STARTING|PACKAGE_READY|RESOURCE_INIT|BOOTSTRAP|OTHER",
  "preferenceKeys": ["pref1", "pref2"],
  "reasonCode": "controlled enum",
  "reason": "specific technical explanation",
  "coveredCallSites": ["path/to/File.kt:42:funcName", "path/to/File.kt:43:funcName"],
  "hookTargets": ["com.android.server.Foo#bar"],
  "testEvidence": ["tools/tests/test_legacy_exception_registry.py"],
  "exitCondition": "specific condition for migration or removal"
}
```

Validation rejects:
- empty or unknown `owner`, `sourceFile`, `entrypoint`, `process`, `phase`, `reasonCode`, `reason`, `testEvidence`, `exitCondition`;
- non-existent `sourceFile` or `entrypoint` (function not found in source);
- duplicate `id`;
- duplicate call site covered by more than one exception;
- typed-catalog-owned call sites registered as legacy;
- `API_BRIDGE` or `INSTALLER_INFRASTRUCTURE` calls masquerading as business `LEGACY_EXCEPTION`;
- unknown `process`/`phase`/`reasonCode`;
- `exitCondition` equal to "never".

## Reason taxonomy

Initial controlled `reasonCode` values:

- `CROSS_PROCESS` — feature must route to multiple incompatible processes and no typed owner currently supports the split.
- `LIFECYCLE_BOOTSTRAP` — hook is installed from a bootstrap/installer entrypoint without a typed Feature route.
- `RESOURCE_HOOK` — hook targets resource replacement or `setResReplacement` and is owned by the resource hook subsystem.
- `DYNAMIC_TARGET_SET` — target class/method set is determined dynamically (cloud, runtime ROM detection, user list) and cannot be expressed as a stable contract.
- `SHARED_MUTABLE_STATE` — hook shares mutable state across multiple features and must be refactored before typed ownership.
- `ROM_DEPENDENT_DISPATCH` — dispatch depends on ROM-specific runtime conditions not yet modeled in contracts.
- `API_BRIDGE_BOUNDARY` — call lives inside `ModuleHelper`/`XposedHelpers` bridge; these remain `API_BRIDGE`, not business exceptions.
- `INSTALLER_INFRASTRUCTURE` — call lives in generic installer/bootstrap code; these remain `INSTALLER_INFRASTRUCTURE`, not business exceptions.
- `TEMPORARY_MIGRATION_DEFERRED` — migration is technically possible but intentionally deferred to a specific later Task Slice.
- `DEAD_CODE_PENDING_OWNER_APPROVAL` — source entrypoint appears unreachable but will be deleted only with mechanical evidence and owner approval.
- `OTHER_REVIEW_REQUIRED` — reason is documented but requires a future `a13-independent-review` pass.

`API_BRIDGE` and `INSTALLER_INFRASTRUCTURE` must not be listed as business `LEGACY_EXCEPTION` unless the registry is recording a deliberate cross-boundary relationship with a specific exit condition.

## Process/phase taxonomy

Allowed `process` values:
- `system_server`
- `system_ui`

Allowed `phase` values:

## Test evidence rules

Each exception record must include at least one test or validator that proves:
- the covered call sites exist in source;
- the owner is the correct entrypoint;
- the call site is not owned by the typed catalog;
- the call site is not `API_BRIDGE` or `INSTALLER_INFRASTRUCTURE`.

## Exit condition rules

`exitCondition` must be a specific, verifiable statement, e.g.:
- "Migrate to typed FeatureSpec when cross-process installer routing is available (P3.3C)."
- "Delete after owner confirms no references exist (P3.4)."
- "Refactor into contract with dynamic target resolution (P3.5)."

## Batching plan (P3.3B/C...)

Tentative next batches after P3.3A:
- P3.3B: cross-process and lifecycle-bootstrap exceptions (e.g., `system_separatevolume`, `USBConfig`, `AlarmCompatService`, `GlobalActions` main actions).
- P3.3C: per-file mixed exceptions where typed and legacy calls coexist; split typed and legacy call sites cleanly.
- P3.3D: resource hook and dynamic target set exceptions.
- P3.3E: dead code and review-required exceptions.

## Mutation cases

Validator and tests must reject:
1. Missing `owner`.
2. Missing `process`.
3. Missing `phase`.
4. Missing `reasonCode` or `reason`.
5. Missing `testEvidence`.
6. Missing `exitCondition`.
7. Duplicate `id`.
8. One call site assigned to two exceptions.
9. Typed-catalog-owned call site added as legacy.
10. `API_BRIDGE` / `INSTALLER_INFRASTRUCTURE` call disguised as business exception.
11. Non-existent `sourceFile`.
12. Non-existent `entrypoint` (function not in source).
13. Unknown `process`/`phase`/`reasonCode`.
14. Windows and Linux path normalization mismatch.
15. Registry and inventory output order instability.
16. All `UNKNOWN` calls automatically downgraded to exceptions.
